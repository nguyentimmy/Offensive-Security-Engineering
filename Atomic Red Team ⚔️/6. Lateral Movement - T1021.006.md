# 🧪 Validation Walkthrough — T1021.006: Windows Remote Management


### 📖 Why it matters

Windows Remote Management (WinRM) is Microsoft's built-in remote admin protocol — and an attacker favorite for lateral movement. It's **fileless remote code execution** over HTTP(S) on ports 5985/5986, often enabled by default in enterprises where DSC, Ansible, or WSUS need it. Unlike PsExec (drops a service binary) or SMB (leaves share artifacts), WinRM leaves almost nothing behind — validating detection here proves you can catch the pivot before it becomes domain-wide compromise.

**Tactic:** Lateral Movement, Execution
**Technique:** [T1021.006 — Remote Services: Windows Remote Management](https://attack.mitre.org/techniques/T1021/006)

### ⚔️ The Atomic Tests

We validate three tests spanning both PowerShell and native remoting — the same variants attackers pick between based on what's available:

| # | Test | Platform | What it does |
| --- | --- | --- | --- |
| 1 | `Invoke-Command` remote execution | Windows | Runs a single command or scriptblock on a remote host — fire-and-forget |
| 2 | `Enter-PSSession` interactive shell | Windows | Opens an interactive PowerShell session to a remote host — hands-on-keyboard |
| 3 | `winrs` native remote execution | Windows | Same result as Test 1 without PowerShell — uses the native `winrs.exe` binary |

---
### 🔬 Test 1 — `Invoke-Command` remote execution

The most common attacker use of WinRM. A single `Invoke-Command` runs whatever you want on a target host and returns the output — no session to maintain, no artifacts on disk. This is the "reach out, run something, come back" primitive that attackers chain to enumerate, dump credentials, or drop a beacon on the next host.

**Attack commands** (`powershell`):

```powershell
Invoke-Command -ComputerName <target> -ScriptBlock { hostname; whoami; ipconfig }
```

**Cleanup:** None — no persistent artifacts.

---
### 🔬 Test 2 — `Enter-PSSession` interactive shell

The interactive variant. `Enter-PSSession` gives the attacker a live PowerShell prompt on the remote host — same experience as SSH on Linux. Great for hands-on-keyboard operators exploring a newly-reached target. Session logs on the target capture the commands, but only if PowerShell script-block logging is on.

**Attack commands** (`powershell`):

```powershell
Enter-PSSession -ComputerName <target>
```

**Cleanup:**

```powershell
Exit-PSSession
```

---

### 🔬 Test 3 — `winrs` native remote execution

The same result as Test 1, but via the native `winrs.exe` binary instead of PowerShell. Worth validating separately because detections that only alert on `powershell.exe -ComputerName` miss this variant entirely. Any decent lateral-movement detection has to catch the underlying WinRM traffic, not just the PowerShell path.

**Attack commands** (`command_prompt`):

```cmd
winrs -r:<target> "hostname & whoami & ipconfig"
```

**Cleanup:** None.

---

### ✅ What to validate after running

Confirm your detections surface:

- **Endpoint (source):** process creation for `powershell.exe -ComputerName`, `Enter-PSSession`, and `winrs.exe` in `DeviceProcessEvents` (Event ID 4688).
- **Network:** outbound connections to **5985/HTTP** or **5986/HTTPS** on the target host.
- **Target-side auth:** Event ID **4624 Logon Type 3** (network) from the source, plus **WSMan operational logs** (Event IDs 91, 168).

**Did all three tests fire?** If Test 3 (`winrs`) slipped past a PowerShell-keyed rule, add a detection on the native binary too.

> 💡 The cleanest lateral-movement detection keys on the **network path** (a source workstation opening 5985/5986 to a server it's never talked to before) combined with the **target-side network logon** — because that pattern catches every WinRM variant, PowerShell or native, present or future.
