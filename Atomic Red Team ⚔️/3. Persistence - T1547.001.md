# 🧪 Validation Walkthrough — T1547.001: Registry Run Keys / Startup Folder


### 📖 Why it matters

Registry Run keys and the Startup folder are the **single most common persistence technique** in real-world intrusions. Every commodity RAT, infostealer, and ransomware loader touches one of these at some point — because Windows checks them at every boot or user logon and automatically runs whatever's listed. The technique is native, requires no elevation for HKCU, and blends into constant legitimate use (Chrome updater, Teams, OneDrive, printer software, and Adobe products all set Run keys during install). That noise is exactly why validating detection here matters: if your SIEM/EDR can't separate a legit installer setting a Run key from `powershell.exe` writing one that points to `%TEMP%`, an attacker walks past your persistence detection every time.

**Tactic:** Persistence, Privilege Escalation
**Technique:** [T1547.001 — Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder](https://attack.mitre.org/techniques/T1547/001)

### ⚔️ The Atomic Tests

We validate the first three tests under this technique:

| # | Test | Platform | What it does |
| --- | --- | --- | --- |
| 1 | Reg Key Run | Windows | Adds a value under `HKCU\...\CurrentVersion\Run` that fires at every user logon |
| 2 | Reg Key RunOnce | Windows | Adds a value under `HKCU\...\CurrentVersion\RunOnce` that fires once at the next logon |
| 3 | PowerShell registry Run key | Windows | Uses `New-ItemProperty` to write a Run key from PowerShell instead of `reg.exe` |

---
### 🔬 Test 1 — Reg Key Run

The classic — a single `reg add` to the user's `Run` key. Anything listed here executes every time the user logs on. Detection has to survive the fact that legitimate applications write to this key constantly during install and update; the tell is *what* is being written and *by whom*.

**Attack commands** (`command_prompt`):

```cmd
reg add HKCU\Software\Microsoft\Windows\CurrentVersion\Run /v "AtomicRedTeam" /t REG_SZ /d "C:\Path\To\Executable.exe" /f
```

**Cleanup:**

```cmd
reg delete HKCU\Software\Microsoft\Windows\CurrentVersion\Run /v "AtomicRedTeam" /f
```
---
### 🔬 Test 2 — Reg Key RunOnce

The one-shot variant — `RunOnce` fires the value on the **next** logon and then removes itself. Attackers use this for stagers that only need to execute once (e.g., to unpack a second-stage payload). Because it's self-deleting, it's easier to miss on retrospective hunts, which is exactly why real-time detection on the write matters.

**Attack commands** (`command_prompt`):

```cmd
reg add HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce /v "AtomicRedTeam" /t REG_SZ /d "C:\Path\To\Executable.exe" /f
```

**Cleanup:**

```cmd
reg delete HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce /v "AtomicRedTeam" /f
```
---

### 🔬 Test 3 — PowerShell registry Run key

Same result, different tool — `New-ItemProperty` writes the Run key from PowerShell instead of `reg.exe`. Worth validating separately because detections that only alert on `reg.exe` command lines miss this variant entirely. A robust detection keys on the **registry write event itself** (Event ID 4657 / `DeviceRegistryEvents`), not on the tool used to write it.

**Attack commands** (`powershell`):

```powershell
New-ItemProperty -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run" -Name "AtomicRedTeam" -Value "C:\Path\To\Executable.exe" -PropertyType String -Force
```

**Cleanup:**

```powershell
Remove-ItemProperty -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run" -Name "AtomicRedTeam" -Force
```

---

### ✅ What to validate after running

Each test should generate telemetry your detections can key on. After execution, confirm:

- **Did the SIEM/EDR alert?** Registry writes to Run/RunOnce should surface as **Windows Event ID 4657** (registry value modified), Sysmon **Event ID 13** (registry value set), or in `DeviceRegistryEvents` on MDE. The action type will be `RegistryValueSet` with `RegistryKey` matching `...\CurrentVersion\Run` or `RunOnce`.
- **Was the severity right?** A Run key value pointing to `C:\Program Files\...` from an installer parent is routine. A Run key value written by `powershell.exe`, `cmd.exe`, or an Office child process — especially one pointing to `%TEMP%`, `%APPDATA%`, or `\Downloads\` — should score much higher.
- **Did detection catch both `reg.exe` AND PowerShell paths (Test 1/2 vs Test 3)?** If Test 3 slipped through, your detection is keyed on the *tool* instead of the *registry write*. Fix by targeting the registry event.
- **If nothing fired** — that's the gap. Build a detection on registry writes to Run/RunOnce keys, filtered by suspicious value data (user-writable paths, script-host executables) or suspicious parent processes.

> 💡 A clean detection here keys on the **combination**: a write to a Run/RunOnce key **+** a value pointing to a user-writable path or script host **+** an unusual parent process. Any one alone is noise — Chrome, Teams, and OneDrive all set Run keys legitimately. The tell is who's writing it and what it points to.
