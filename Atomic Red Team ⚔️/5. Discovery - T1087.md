# 🧪 Validation Walkthrough — T1087: Account Discovery


### 📖 Why it matters

The moment an attacker lands on a host, the first question they ask is *"who else is here?"* — and account discovery is how they answer it. Enumerating local users, domain users, and privileged groups tells them which accounts to target for credential theft, which admins to impersonate, and where lateral movement is worth trying. Every hands-on-keyboard intrusion runs some flavor of this within the first few minutes. The problem for defenders: every one of these commands (`net user`, `net group`, `Get-ADUser`) is used by legitimate admins constantly, so the signal isn't the command itself — it's the **context** (unusual parent, non-admin account, burst of enumeration in a short window). Validating detection here proves you can spot the difference between routine admin work and pre-lateral-movement recon.

**Tactic:** Discovery
**Technique:** [T1087 — Account Discovery](https://attack.mitre.org/techniques/T1087) (parent technique — sub-techniques: `.001` Local Account, `.002` Domain Account)

### ⚔️ The Atomic Tests

We validate three tests spanning both local and domain enumeration — the same span an attacker exercises after landing on a host:

| # | Test | Platform | What it does |
| --- | --- | --- | --- |
| 1 | Local account enumeration (`net user`) | Windows | Lists every local user account on the host |
| 2 | Domain account enumeration (`net user /domain`) | Windows | Lists every account in the domain, straight from a workstation |
| 3 | Domain account enumeration via PowerShell | Windows | Same result as Test 2 using `Get-ADUser` — bypasses `net.exe`-only detections |

---
### 🔬 Test 1 — Local account enumeration (`net user`)

The classic. A single `net user` returns every local account on the host — a quick way for an attacker to spot the local admin, any leftover service accounts, or the "helpdesk" account that never got cleaned up. Legit admins run this too, so detection has to rely on context (who ran it, from where, and what else was run in the same window).

**Attack commands** (`command_prompt`):

```cmd
net user
```

**Cleanup:** None — read-only enumeration, nothing to clean up.

---
### 🔬 Test 2 — Domain account enumeration (`net user /domain`)

Same tool, wider blast radius — the `/domain` flag makes `net.exe` query the domain controller and return every user account in Active Directory. This is one of the most common early recon commands in real intrusions because it works from any domain-joined workstation with no elevation required. Detection here matters even more than Test 1 because a standard user running domain-wide enumeration is almost never legitimate.

**Attack commands** (`command_prompt`):

```cmd
net user /domain
```

**Cleanup:** None.

---

### 🔬 Test 3 — Domain account enumeration via PowerShell

Same result, different tool — `Get-ADUser -Filter *` pulls every user from AD via the ActiveDirectory PowerShell module. Worth validating separately because detections that only alert on `net.exe` command lines miss this variant completely. A robust detection keys on the **behavior** (mass account enumeration from a non-admin context), not on which binary was used.

**Attack commands** (`powershell`, RSAT / ActiveDirectory module required):

```powershell
Get-ADUser -Filter * | Select-Object SamAccountName, Enabled, LastLogonDate
```

**Cleanup:** None.

---

### ✅ What to validate after running

Each test should generate telemetry your detections can key on. After execution, confirm:

- **Did the SIEM/EDR alert?** Enumeration commands surface as **Windows Event ID 4688** (process creation) or `DeviceProcessEvents` in Defender for Endpoint, with `FileName` = `net.exe` or `powershell.exe` and the command line matching enumeration verbs. Domain queries also generate directory-service logs (4662) on the domain controller.
- **Was the severity right?** A single `net user` from an admin during business hours is noise. A burst of enumeration commands (`net user`, `net group`, `net user /domain`, `net localgroup Administrators`) from a **standard user account** or an **Office child process** in a short window is high severity — that's active recon.
- **Did all three tests fire?** If Test 1 and 2 fired but Test 3 (PowerShell) didn't, your detection is keyed on `net.exe` command lines and misses the PowerShell path. Fix by adding a rule that catches `Get-ADUser` / `Get-ADGroup` / `Get-ADComputer` mass queries, or key on directory-service telemetry from the DC instead of endpoint command lines.
- **If nothing fired** — build a detection on enumeration bursts (multiple discovery commands from one process/account within a short window), filtered by unusual parent process or non-admin account context.

> 💡 A clean detection here keys on the **combination**: a burst of enumeration commands **+** an unusual parent process (Office, script host) or a non-admin account **+** a short time window. Any single `net user` or `Get-ADUser` is noise — admins run these constantly. The tell is the *pattern*: many enumeration commands stacked together from an account or process that shouldn't be doing recon.
