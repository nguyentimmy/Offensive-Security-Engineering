# 🧪 Validation Walkthrough — T1003.001: LSASS Memory


### 📖 Why it matters

LSASS (`lsass.exe`) is the process that holds Windows credentials in memory — plaintext passwords, hashes, and Kerberos tickets for every user with an active session on the host. Getting a memory dump of LSASS is the fastest, most direct way for an attacker to harvest credentials, and it's what turns a single compromised endpoint into domain-wide access via lateral movement. Almost nothing legitimate opens LSASS for read/dump — the list of legit accessors is short (AV, some Windows internals) — which makes this one of the highest-fidelity detections you can build. That short list is exactly why validating it matters: if your EDR/SIEM misses an unexpected process reading LSASS, an attacker gets domain admin on their first pivot.

**Tactic:** Credential Access
**Technique:** [T1003.001 — OS Credential Dumping: LSASS Memory](https://attack.mitre.org/techniques/T1003/001)

### ⚔️ The Atomic Tests

We validate the first three tests under this technique — each uses a different tool class, so together they stress your detection from three angles:

| # | Test | Platform | What it does |
| --- | --- | --- | --- |
| 1 | ProcDump | Windows | Uses the signed Sysinternals `procdump` tool to write LSASS memory to disk |
| 2 | comsvcs.dll MiniDump | Windows | LOLBin abuse — `rundll32` calls the built-in `comsvcs.dll` MiniDump export |
| 3 | Direct syscalls / API unhooking | Windows | Uses a tool like Dumpert to bypass user-mode API hooks that EDRs rely on |

---
### 🔬 Test 1 — ProcDump

The signed-tool variant. `procdump.exe` is a legitimate Sysinternals utility used by developers and IT — but the same `-ma lsass.exe` command that helps a sysadmin troubleshoot is what an attacker runs to steal every credential on the host. Because the binary is signed, this test validates whether your detection keys on **behavior** (a process opening LSASS with dump rights) rather than on the tool name alone.

**Attack commands** (elevated `command_prompt`):

```cmd
procdump.exe -accepteula -ma lsass.exe C:\Windows\Temp\lsass_dump.dmp
```

**Cleanup:**

```cmd
del C:\Windows\Temp\lsass_dump.dmp /f /q
```
---
### 🔬 Test 2 — comsvcs.dll MiniDump

The LOLBin classic. `comsvcs.dll` ships with Windows and exposes a `MiniDump` function, so `rundll32` alone can dump LSASS with no external tools dropped to disk. This is one of the most-abused living-off-the-land patterns in the wild — validating detection here confirms your rules catch the built-in path, not just third-party dumpers.

**Attack commands** (elevated `command_prompt`, run as `SYSTEM`):

```cmd
rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump <LSASS_PID> C:\Windows\Temp\lsass_dump.dmp full
```

**Cleanup:**

```cmd
del C:\Windows\Temp\lsass_dump.dmp /f /q
```
---

### 🔬 Test 3 — Direct syscalls / API unhooking

The evasion variant. Tools like **Dumpert** use direct system calls to skip the standard Windows APIs that EDR products hook — meaning command-line detections and user-mode API monitoring can miss the dump entirely. This test validates the **fallback** detection path: process-handle access to `lsass.exe` (kernel-level telemetry that direct syscalls can't hide from).

**Attack commands** (elevated `command_prompt`):

```cmd
Outflank-Dumpert.exe
```

**Cleanup:**

```cmd
del dumpert.dmp /f /q
```

---

### ✅ What to validate after running

Each test should generate telemetry your detections can key on. After execution, confirm:

- **Did the SIEM/EDR alert?** The high-fidelity signal is a **process handle open to `lsass.exe` with read/dump rights**. In Defender for Endpoint, that surfaces in `DeviceEvents` as `ActionType == "OpenProcessApiCall"` with `FileName =~ "lsass.exe"`. Sysmon **Event ID 10** captures the same thing. Access-rights masks like `0x1010` or `0x1410` are the classic dump combinations.
- **Was the severity right?** Any unexpected process reading LSASS should be Critical — the list of legit accessors is short (MsMpEng, wininit, csrss, services, LSA). Anything outside that list touching LSASS with dump rights is nearly always malicious.
- **Did all three tests fire?** If Test 1 (ProcDump) fired but Test 2 (comsvcs) or Test 3 (Dumpert) didn't, your detection is keyed on tool names or command lines — not on the underlying handle access. That's the gap: a detection built on `procdump` strings misses the LOLBin and syscall variants entirely.
- **If nothing fired** — build a detection on `OpenProcessApiCall` to `lsass.exe`, excluding the known-good accessor list, then re-run all three tests.

> 💡 The strongest LSASS detection ignores the tool entirely and keys on the **handle access event** itself — because the list of processes that legitimately read LSASS memory is tiny and known. A detection built on `OpenProcessApiCall to lsass.exe with dump rights` catches ProcDump, comsvcs, Dumpert, Mimikatz, and every future tool that hasn't been named yet, because they all have to open that handle to steal the credentials.
